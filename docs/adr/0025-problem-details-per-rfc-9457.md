# 25. Problem details per RFC 9457

Status: Accepted
Date: 2026-10-26

## Context and Problem Statement

The API has answered errors as `application/problem+json` since ADR-0013, and ADR-0021 carries the
same members over GraphQL, gRPC and the broker RPC. A review against RFC 9457 found gaps:

- The type was the relative URI `/problems/<reason>`. RFC 9457 recommends absolute type URIs and
  asks that a type that is a locator lead to documentation. `/problems/exceeds-credits` resolves
  to an http URL of the API, which answered 404.
- No document defined the problem types. Section 4 asks each definition to state its type URI,
  title and HTTP status.
- `about:blank` problems had titles such as "Not found". Section 4.2.1 makes the title the status
  phrase ("Not Found").
- Every error Huma raised below 500 became `400 invalid-request`: a body over the size limit
  answered 400, not 413.
- `instance` was the decoded path, so `/things/a%20b` became `/things/a b`, which is not a URI
  reference.
- A body decoding error quoted encoding/json ("cannot unmarshal string into Go struct field
  thingRequest.code of type int"), which describes the service rather than the request.
- GraphQL errors gqlgen raised itself (parse, validation, limits) carried no type, title or status,
  and a body that was not a GraphQL request was quoted back in the error message.
- `GET /readyz` answered its 503 as `application/json`, the only error status that was not a
  problem.

This record replaces only these parts: in ADR-0013, the form of the problem type; in ADR-0018,
"no `errors` array", the mapping of every Huma input error to 400, and the JSON 503 body of
`/readyz`; in ADR-0021, the derivation of the ErrorInfo reason from the `/problems/` slug and the
GraphQL errors gqlgen raises itself. The reasons, kinds, statuses and extension members of every
other problem stand.

## Decision Drivers

- Follow RFC 9457, including its SHOULDs and RECOMMENDEDs, where it costs no transport its idiom.
- A problem type stays an identifier clients switch on: the same string in every deployment.
- One catalogue of problem types, generated from the code, so docs and code cannot drift.
- No driver text and no Go internals reach a client (AGENTS.md).

## Considered Options

For the type URI:

1. Keep `/problems/<reason>` and serve a documentation page at `GET /problems/{reason}`.
2. An absolute URI built from a configured public URL of the API, with the same docs route.
3. A fixed absolute URI: the entry of the problem in a catalogue published in the repository
   (chosen).

Option 1 keeps the relative form RFC 9457 advises against. Option 2 gives the same problem a
different type in each deployment, so clients would match on the slug instead of the type, and
every transport would need the configured base. Option 3 is absolute and the same everywhere, it
opens human-readable documentation, and it needs no configuration or route.

## Decision Outcome

Chosen option: 3.

- The type is `https://github.com/wilfriedago/tigerbeetle-platform/blob/develop/docs/problems.md#<reason>`
  (`problem.TypeBase` in Go, `PROBLEM_TYPE_BASE` in the api-client). `docs/problems.md` is
  generated by `cmd/problemdocs`, without cgo, from `problem.Definitions()` (reason, title,
  status, description) and, for the TigerBeetle results a declined chain reports under their own
  name, from `bookkeeping/domain.TransferResults`. A test of the TigerBeetle adapter keeps that
  list equal to the client's. Each reason is a heading, which GitHub turns into the fragment.
  `just generate` writes the file and `just generate-check` fails on drift.
- `about:blank` stays the type of a problem the status describes on its own (unknown route,
  wrong method, oversized body, fault of the service), with the status phrase as its title.
- Huma's own errors keep their status: 400 and 422 (a request it could not decode) become
  `invalid-request` with an `errors` extension member, an array of `{detail, pointer}` for the
  body (a JSON Pointer in URI fragment form, as in the RFC's example) or `{detail, parameter, in}`
  for a parameter. Any other status is `about:blank` with Huma's message as the detail. The
  domain's own validation keeps a single `detail`; it runs the same way on every transport.
- The REST decoder rewords encoding/json errors as "expected integer, got string" at the pointer
  of the member.
- `instance` is the escaped request path, a relative URI reference; `requestId` identifies the
  occurrence.
- `GET /readyz` answers its 503 as a `not-ready` problem with `dependencies` as an extension
  member. The 200 body is unchanged.
- GraphQL: the errors gqlgen raises carry the members of `invalid-request` and keep their code. A
  body that is not a JSON object, cannot be read or exceeds the limit is answered by the handler
  itself as problem+json (400 or 413), before gqlgen.
- gRPC and the broker RPC carry the absolute type unchanged. The ErrorInfo reason is derived from
  the reason itself (`exceeds-credits` gives `EXCEEDS_CREDITS`), not from the type URI.

### Consequences

- Breaking for clients that compared `type` with `/problems/...` strings, and for readers of the
  503 body of `/readyz`. The console and the api-client are updated in the same change; the
  api-client gains `problemTypeOf`, `problemReason` and `ApiError.reason`.
- The type points at the `develop` branch of the public repository. A rename of the repository,
  the branch or the file changes every type, so none of them moves without a new ADR.
- Adding a problem reason means adding its definition to `internal/platform/problem/catalog.go`
  and running `just generate`; the test of `cmd/problemdocs` fails for a reason without a
  heading.
- The plain-text 400 and 431 that net/http writes for a malformed request line or oversized
  headers happen before any handler runs and stay outside this record.
